# CAN 실무 펌웨어 스타터

CAN 펌웨어를 **처음부터 손으로 시작하기 위한 최소 골격**이다.
하드웨어 없이 지금 바로 빌드하고 시험할 수 있다.

```bash
make test     # 호스트 단위시험 (MCU 불필요)
make demo     # SocketCAN 데모 빌드 — 아래 2단계 참고
```

STD-FW-001(사내 펌웨어 코딩 표준)의 계층 구조와 규칙을 따르는 참조 구현이기도 하다.

---

## 왜 이 순서인가

CAN을 처음 하는 사람이 가장 흔히 밟는 경로는 "MCU 예제 프로젝트를 열고 CAN 예제를
돌려본다"이다. 이 길은 **통신이 안 될 때 원인을 좁힐 수 없다**는 문제가 있다.
비트 타이밍인지, 종단저항인지, 필터 설정인지, 내 코드인지 구분이 안 된다.

그래서 순서를 뒤집는다. **하드웨어에 의존하지 않는 계층을 먼저 완성하고**,
하드웨어는 마지막에 붙인다. 그러면 문제가 생겼을 때 남은 변수가 하나뿐이다.

---

## 학습 순서

### 0단계 — 장비를 먼저 정한다 (반나절)

| 항목 | 최소 | 권장 |
|---|---|---|
| 버스 관찰 | `candump` + USB-CAN 어댑터 (3~10만원) | Vector VN1610 / PCAN-USB |
| 노드 | MCU 보드 1개 | 같은 보드 2개 |
| 종단저항 | 120 Ω 2개 — **없으면 통신이 되다 말다 한다** | 스위치형 종단 보드 |
| 오실로스코프 | 없어도 시작은 된다 | 100 MHz 이상, 파형으로 봐야 풀리는 문제가 있다 |

> 어댑터 없이 시작할 수 있는 유일한 방법이 리눅스 `vcan`이다. 2단계에서 쓴다.

### 1단계 — 하드웨어 없이 계층을 만든다 (이 레포)

```bash
make test
```

`app/`, `comm/` 계층을 호스트에서 전부 작성하고 시험한다. 이 단계에서 끝내야 하는 것:

- 신호 인코딩·디코딩 (`can_signal.c`) — Intel/Motorola 비트 순서, 스케일·오프셋
- 수신 디스패치, 주기 송신, 수신 타임아웃 (`can_if.c`)
- 애플리케이션 로직 (`app_speaker.c`)

가짜 CAN 컨트롤러(`port/port_loopback.c`)가 프레임 주입과 송신 확인 훅을 제공하므로
버스 상황을 전부 시뮬레이션할 수 있다. Bus-Off, 큐 넘침, 타임아웃까지.

### 2단계 — 가상 버스로 진짜 소켓 통신 (리눅스)

```bash
sudo modprobe vcan
sudo ip link add dev vcan0 type vcan
sudo ip link set up vcan0

make demo && ./build/demo          # 터미널 1
candump vcan0                       # 터미널 2
cansend vcan0 120#0346              # 터미널 3 — sound_id=3, volume=70
```

여기서 배우는 것: 프레임 포맷, ID 필터, 주기 송신이 실제로 어떻게 보이는지.
아직 전기적 문제는 하나도 없으므로 **순수하게 프로토콜만** 다룬다.

### 3단계 — MCU 1개, 루프백 모드

`port/port_stm32g4.c` 같은 실제 포트를 작성한다. 컨트롤러를 **내부 루프백 모드**로
두면 트랜시버와 버스 없이 자기가 보낸 프레임을 자기가 받는다.
여기서 검증하는 것은 딱 하나 — **레지스터 설정이 맞는가**.

### 4단계 — 비트 타이밍을 맞춘다

가장 많이 막히는 지점이다. 공식은 하나다.

```
비트 시간 = Sync_Seg(1 tq) + Prop_Seg + Phase_Seg1 + Phase_Seg2
총 tq 수 = 8 ~ 25
BRP      = f_clk / (bitrate × 총 tq 수)
샘플 포인트 = (1 + Prop_Seg + Phase_Seg1) / 총 tq 수
```

**예: STM32G4, FDCAN 커널 클럭 80 MHz, 500 kbps, 샘플 포인트 87.5%**

```
총 tq 수 = 16  →  BRP = 80,000,000 / (500,000 × 16) = 10
샘플 포인트 87.5% → 샘플 전 14 tq
   Sync_Seg = 1
   TSEG1    = 13      (Prop_Seg + Phase_Seg1)
   TSEG2    = 2
   SJW      = 1 ~ 2   (TSEG2 이하)
검산: (1 + 13) / 16 = 0.875 ✓
```

| 규격 | 권장 샘플 포인트 |
|---|---|
| CiA 301 / CANopen | 87.5 % |
| SAE J1939 | 87.5 % |
| 자동차 OEM 일반 | 80 ~ 87.5 % |

> **버스의 모든 노드가 같은 비트레이트와 비슷한 샘플 포인트여야 한다.**
> 샘플 포인트가 크게 어긋난 노드가 하나 있으면, 그 노드만 에러를 내는 게 아니라
> 버스 전체에 에러 프레임이 깔린다.

### 5단계 — 2노드 통신

종단저항 120 Ω을 **양 끝에 하나씩** 붙인다. 버스 전체 저항은 60 Ω이 되어야 한다.
멀티미터로 먼저 확인하고 전원을 넣는다. 이 한 가지로 초보 단계 문제의 절반이 사라진다.

### 6단계 — DBC를 도입한다

이 시점부터 신호 정의를 **손으로 쓰지 않는다.** DBC 파일을 원본으로 삼고 코드를 생성한다.

```bash
pip install cantools
cantools generate_c_source speaker.dbc
```

`can_signal.c`는 생성기가 무엇을 만드는지 이해하기 위한 참조 구현이며,
실무 코드에서는 생성물로 대체된다 (STD-FW-001 FW-COM-001).

### 7단계 — 오류 처리

- TEC/REC 오류 카운터 읽기, Error Active → Passive → Bus-Off 전이 관찰
- Bus-Off에서 **즉시 복구하지 않는다** — 원인이 남아 있으면 복구·재진입을 반복하며
  버스를 더 망가뜨린다. `can_if.c`의 `service_bus_state()` 참고
- 배선을 일부러 끊어 보고, 종단을 빼 보고, 비트레이트를 틀리게 해 본다.
  **고장을 만들어 본 사람만 현장에서 원인을 찾는다.**

### 8단계 — 진단 계층

ISO-TP(ISO 15765-2) → UDS(ISO 14229) 순서로 올린다. 8바이트를 넘는 데이터를
분할 전송하는 것이 ISO-TP이고, 그 위에서 진단 서비스를 정의한 것이 UDS다.
자체 구현한다면 상태 전이표를 먼저 그리고 단위시험부터 만든다.

### 9단계 — 부트로더

UDS 기반 펌웨어 업데이트. 여기까지 오면 실무에서 요구하는 범위를 대부분 덮는다.

## 이 레포의 구조

```
include/
  can_hal.h       컨트롤러 추상화 — 벤더 헤더를 포함하지 않는다
  can_if.h        송수신 서비스 (디스패치 · 주기송신 · 타임아웃 · Bus-Off)
  can_signal.h    비트 단위 신호 인코딩 · 디코딩
  app_speaker.h   예제 애플리케이션 (CAN 스피커 노드)
src/
  can_signal.c    Intel · Motorola 비트 배열 참조 구현
  can_if.c        서비스 계층
  app_speaker.c   애플리케이션 — MCU를 전혀 모른다
  main_demo.c     SocketCAN 데모 진입점
port/
  port_loopback.c 호스트용 가짜 컨트롤러 (+ 시험 훅)
  port_socketcan.c 리눅스 SocketCAN 구현
test/
  test_main.c     단위시험 200건
```

계층 규칙은 하나다. **상위는 하위만 호출하고, 벤더 SDK는 `port/`에만 있다.**
`app/`과 `comm/`이 MCU를 모르기 때문에 호스트에서 전부 시험된다.

## 예제 통신 규격

| ID | 이름 | 방향 | 주기 |
|---|---|---|---|
| `0x120` | SPEAKER_CMD | 수신 | 100 ms (타임아웃 500 ms) |
| `0x121` | SPEAKER_STATUS | 송신 | 100 ms |

**SPEAKER_CMD**

| 신호 | 시작 비트 | 길이 | 범위 |
|---|---|---|---|
| sound_id | 0 | 8 | 0 ~ 255 |
| volume | 8 | 7 | 0 ~ 100 % |
| repeat | 15 | 1 | — |

**SPEAKER_STATUS**

| 신호 | 시작 비트 | 길이 | 비고 |
|---|---|---|---|
| state | 0 | 3 | IDLE / PLAYING / SAFE |
| fault | 3 | 2 | NONE / OPEN / SHORT |
| cur_sound | 8 | 8 | |
| cur_volume | 16 | 7 | |
| temp_c | 24 | 8 | factor 1, offset −40 |
| counter | 48 | 4 | 롤링 카운터 |
| checksum | 56 | 8 | 바이트 0..6 XOR |

롤링 카운터와 체크섬은 자동차에서 표준 관행이다. 수신 측이 **프레임 손상**과
**송신 노드 정지**를 구분할 수 있게 해 준다. 값이 그대로면 노드가 멈춘 것이고,
체크섬이 틀리면 전송이 깨진 것이다.

## 흔히 밟는 지뢰

| 증상 | 대개의 원인 |
|---|---|
| 아무것도 수신되지 않는다 | 종단저항 없음 / 비트레이트 불일치 / CAN_H·CAN_L 반전 |
| 가끔만 수신된다 | 샘플 포인트 불일치, 종단 1개만 설치 |
| 송신이 안 나간다 | ACK를 줄 노드가 없음 — CAN은 혼자서는 송신을 완료하지 못한다 |
| 신호값이 엉뚱하다 | Intel/Motorola 혼동, start_bit 기준 오해 |
| 값이 갑자기 뒤집힌다 | 범위를 넘는 물리값을 클램핑 없이 인코딩 (감싸짐) |
| 부팅 직후 오동작 | 초기화 전 0으로 채워진 주기 프레임을 publish |
| Bus-Off 반복 | 복구를 지연 없이 즉시 시도 |

마지막 두 개는 이 레포의 `can_if.c`가 구조적으로 막고 있다.
`armed` 플래그와 `CAN_IF_BUS_OFF_DELAY_MS`를 보면 된다.
