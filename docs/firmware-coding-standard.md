## 1. 목적

본 표준은 사내에서 개발하는 모든 임베디드 펌웨어의 소스 코드가 다음을 만족하도록 하는 것을 목적으로 한다.

1. **안전성** — C 언어의 미정의(undefined) / 미규정(unspecified) / 구현정의(implementation-defined) 동작에 의존하지 않는다.
2. **이식성** — MCU·컴파일러 교체 시 애플리케이션 계층 코드를 수정하지 않는다.
3. **검증 가능성** — 하드웨어 없이 호스트 PC에서 단위 시험이 가능한 구조를 갖는다.
4. **인증 대응성** — ISO 26262(자동차), IEC 62304(의료기기), IEC 61508(산업 일반)이 요구하는 "코딩 표준" 항목에 대한 객관적 증거를 산출한다.

> 본 표준의 준수 자체가 기능안전 인증을 보장하지 않는다. 본 표준은 인증에 필요한 프로세스 중 **코드 작성 및 검증 계층**만을 규정한다.

## 2. 적용 범위

### 2.1 적용 대상

| 구분 | 적용 |
|---|---|
| `app/`, `service/`, `comm/`, `hal/` 계층의 수기 작성 C 소스 | 전면 적용 |
| `port/` 계층 (MCU 의존 구현부) | 전면 적용, 단 벤더 SDK 호출 관련 편차 허용 |
| DBC/ARXML 기반 자동생성 코드 | 미적용 (§14 별도 규정) |
| 3rd-party / SOUP / 벤더 SDK | 미적용 (§2.3 별도 관리) |
| 단위시험 코드, 호스트 전용 도구 | 부분 적용 (§17.4) |

### 2.2 언어 및 컴파일러

- 언어 표준: **C99 (ISO/IEC 9899:1999)** 를 기본으로 한다. C11/C18 사용 시 프로젝트 계획서에 명시한다.
- 컴파일러 확장(`__attribute__`, 인라인 어셈블리 등)은 `port/` 계층에서만 허용하며, 사용 시 편차 기록을 남긴다.
- C++ 를 사용하는 프로젝트에는 본 표준을 적용하지 않는다. 별도로 **MISRA C++:2023** 기반 표준을 제정한다.

### 2.3 적용 제외 코드의 관리

적용 제외 코드는 다음 조건을 모두 만족해야 한다.

1. `third_party/` 또는 `port/vendor/` 하위에만 배치한다.
2. 도입 버전, 출처, 라이선스, 알려진 결함 목록을 `third_party/MANIFEST.md` 에 기록한다.
3. 원본을 수정하지 않는다. 수정이 불가피하면 패치 파일로 분리 보관한다.
4. 의료기기 프로젝트의 경우 IEC 62304 **SOUP 관리 절차**를 추가로 적용한다.

## 5. MISRA C:2023 적용 방침

### 5.1 카테고리별 적용

| MISRA 카테고리 | 사내 적용 | 편차 |
|---|---|---|
| **Mandatory** (약 16개 규칙) | 전면 적용 | 불가 |
| **Required** (대다수) | 전면 적용 | §18 절차로 승인 시 허용 |
| **Advisory** | **부록 B의 지정 목록만 적용** | 기록 권장, 승인 불요 |
| **Directive** (Dir 1.x~4.x) | 전면 적용 | 프로세스 증거로 충족 판정 |

> **Advisory 전면 적용 금지 사유**: 신규 도입 프로젝트에서 Advisory를 모두 활성화하면 초기 위반이 수천 건 발생하여 표준이 사문화된다. 부록 B의 선별 목록으로 시작하고, 프로젝트 성숙도에 따라 확대한다.

### 5.2 Re-categorization

프로젝트 특성상 카테고리를 조정할 경우, **Guideline Enforcement Plan(GEP)** 에 재분류 사유와 함께 기록한다. 단, Mandatory → 하향 조정은 금지한다.

### 5.3 MISRA C:2012 요구 고객사 대응

MISRA C:2023은 MISRA C:2012 + Amendment 1~3 + Technical Corrigendum 1~2 의 통합판으로 **규칙 번호 체계가 호환**된다. 고객사가 MISRA C:2012 준수를 요구하는 경우, GCS에 다음을 명시하여 대응한다.

- 적용 기준: MISRA C:2023
- C:2012 대비 추가/변경 규칙 매핑표 첨부
- C:2012 기준 미해당 규칙에 대한 준수 상태 별도 표기

## 6. 아키텍처 및 계층 규칙

### 6.1 표준 계층 구조

```
app/          도메인 로직. MCU·RTOS·통신 스택에 대한 지식 없음. 호스트 빌드 가능.
service/      스케줄러, 상태머신, 진단(UDS), NVM, 파라미터 관리
comm/         통신 프로토콜 계층 (CAN IF, PDU 라우팅, 신호 매핑, 자동생성 코드)
hal/          하드웨어 추상화 인터페이스 선언 (.h 만 존재)
port/<target>/  hal 인터페이스의 타겟별 구현. 벤더 SDK는 여기서만 사용.
third_party/  외부 도입 코드 (SOUP)
test/         단위시험 및 목(mock)
```

| ID | 구속력 | 규칙 | MISRA |
|---|---|---|---|
| FW-ARC-001 | **[M]** | 상위 계층은 하위 계층만 호출한다. 역방향 호출은 등록된 콜백 또는 이벤트 큐를 통해서만 수행한다. | — |
| FW-ARC-002 | **[M]** | 벤더 SDK 헤더(예: `stm32g4xx_hal.h`, `S32K3xx.h`)는 `port/` 하위에서만 `#include` 한다. | — |
| FW-ARC-003 | **[M]** | `app/` 계층 코드는 MCU 레지스터, 인터럽트, RTOS API를 직접 참조하지 않는다. | — |
| FW-ARC-004 | **[R]** | `app/`, `service/` 계층은 타겟 하드웨어 없이 호스트 컴파일러로 빌드·시험 가능해야 한다. | — |
| FW-ARC-005 | **[R]** | 계층 간 인터페이스는 헤더 파일로만 노출한다. 하위 계층의 내부 헤더를 직접 포함하지 않는다. | — |
| FW-ARC-006 | **[R]** | 순환 의존(circular dependency)을 형성하지 않는다. | — |
| FW-ARC-007 | **[A]** | 재사용 목적의 공통 모듈은 SEooC(ISO 26262-10) 또는 IEC 62304 소프트웨어 항목으로 문서화하여 SOUP 취급을 회피한다. | — |

### 6.2 계층 규칙의 강제

`FW-ARC-002` 는 CI에서 다음과 같이 기계적으로 검사한다.

```bash
# port/ 외부에서 벤더 SDK include 검출 시 빌드 실패
grep -rEn '#include\s*[<"](stm32|s32k|ti_|nrfx|esp_)' \
     --include='*.c' --include='*.h' app/ service/ comm/ hal/ && exit 1 || exit 0
```

## 8. 명명 규칙

| FW-NAM-008 | **[R]** | 포인터 변수에 `p_` 접두사를 붙인다. 예: `p_buffer`. 이중 포인터는 `pp_`. |
| FW-NAM-009 | **[R]** | 전역(파일 정적) 변수에 `s_` 접두사를 붙인다. 예: `s_tick_count`. |
| FW-NAM-010 | **[R]** | 약어는 프로젝트 용어집(`docs/glossary.md`)에 등재된 것만 사용한다. |
| FW-NAM-011 | **[A]** | 반복자 외의 용도로 한 글자 변수명(`a`, `x`)을 사용하지 않는다. 반복자는 `i`, `j`, `k` 를 허용한다. |
| FW-NAM-012 | **[A]** | 이름에 타입을 인코딩하지 않는다(헝가리안 표기법 금지). `p_`, `s_` 접두사는 예외로 허용한다. |

| ID | 구속력 | 지표 | 한계 |
|---|---|---|---|
| FW-CMX-001 | **[R]** | 순환 복잡도 (Cyclomatic Complexity) | 함수당 ≤ 10 |
| FW-CMX-002 | **[R]** | 함수 길이 | ≤ 60 행 (주석·공백 제외) |
| FW-CMX-003 | **[R]** | 블록 중첩 깊이 | ≤ 4 |
| FW-CMX-004 | **[R]** | 함수 파라미터 수 | ≤ 5 |
| FW-CMX-005 | **[R]** | 파일 길이 | ≤ 1000 행 |
| FW-CMX-006 | **[A]** | 팬아웃 (한 함수가 호출하는 함수 수) | ≤ 7 |
| FW-CMX-007 | **[A]** | 행 길이 | ≤ 100 열 |

> ISO 26262-6 Table 1 의 "낮은 복잡도 강제(1a)" 요구는 본 절의 수치 한계로 충족한다. 한계 초과는 §18 편차 절차를 따른다.

### 17.2 주석 및 문서화 (DOC)

| ID | 구속력 | 규칙 |
|---|---|---|
| FW-DOC-001 | **[M]** | 중첩 주석(`/* ... /* ... */`)을 작성하지 않는다. 코드 비활성화에 주석을 사용하지 않는다. |
| FW-DOC-002 | **[R]** | 공개 헤더의 모든 함수·타입에 Doxygen 주석(`@brief`, `@param`, `@return`)을 작성한다. |
| FW-DOC-003 | **[R]** | 구현부 주석은 "무엇을"이 아니라 **"왜"** 를 설명한다. |
| FW-DOC-004 | **[R]** | 편차가 적용된 코드에는 편차 ID를 주석으로 명시한다. (§18.3) |
| FW-DOC-005 | **[R]** | `TODO`, `FIXME` 는 담당자와 이슈 번호를 포함한다. 릴리스 빌드에는 `FIXME` 가 존재하지 않아야 한다. |
| FW-DOC-006 | **[A]** | 주석 처리된 코드를 커밋하지 않는다. 형상관리 이력으로 대체한다. |

### 17.3 빌드 및 정적분석 (BLD / SCA)

| ID | 구속력 | 규칙 |
|---|---|---|
| FW-BLD-001 | **[M]** | 빌드는 IDE 프로젝트 파일이 아닌 스크립트(CMake + 툴체인 파일)로 정의하며, CI에서 재현 가능해야 한다. |
| FW-BLD-002 | **[M]** | 릴리스 바이너리에 형상 식별자(git 해시, 버전, 빌드 일시)를 임베딩하고 진단으로 조회 가능하게 한다. |
| FW-BLD-003 | **[R]** | 컴파일 옵션에 최소 `-Wall -Wextra -Werror -Wconversion -Wshadow -Wundef` 를 포함한다. 경고 0을 유지한다. |
| FW-BLD-004 | **[R]** | 코드 포맷은 `.clang-format` 으로 정의하고, pre-commit 훅과 CI에서 검사한다. |
| FW-SCA-001 | **[M]** | 정적분석 도구는 GEP(§18.1)에 정의된 규칙 세트로 실행하며, 신규 위반 발생 시 CI를 실패시킨다. |
| FW-SCA-002 | **[R]** | 레거시 코드 도입 시 baseline 을 설정하고, 신규/수정 코드에만 게이트를 적용한다. baseline 은 축소 계획과 함께 관리한다. |
| FW-SCA-003 | **[R]** | 기능안전 프로젝트에 사용하는 정적분석 도구는 도구 자격부여(ISO 26262-8 §11) 또는 도구 검증(ISO 13485 §4.1.6) 증빙을 확보한다. |
| FW-SCA-004 | **[A]** | 호스트 빌드에서 AddressSanitizer / UndefinedBehaviorSanitizer 를 단위시험과 함께 실행한다. |

### 17.4 단위시험 (TST)

| ID | 구속력 | 규칙 |
|---|---|---|
| FW-TST-001 | **[M]** | `app/`, `service/` 계층의 모든 공개 함수는 단위시험을 갖는다. |
| FW-TST-002 | **[R]** | 단위시험은 타겟 하드웨어 없이 호스트에서 실행 가능해야 하며, CI에서 자동 실행된다. |
| FW-TST-003 | **[R]** | 시험 프레임워크는 Unity + CMock (Ceedling) 을 기본으로 한다. |
| FW-TST-004 | **[R]** | 커버리지 목표: 일반 프로젝트는 구문 100% / 분기 90% 이상. ISO 26262 ASIL C·D 및 IEC 62304 Class C 프로젝트는 프로젝트 계획서에 MC/DC 등 상향 목표를 별도 규정한다. |
| FW-TST-005 | **[R]** | 현장 불량 및 결함 수정 시, 해당 조건을 재현하는 회귀 시험을 반드시 추가한다. |
| FW-TST-006 | **[R]** | 경계값(최소, 최대, 오버플로 직전), NULL, 미초기화 상태에 대한 시험 케이스를 포함한다. |
| FW-TST-007 | **[A]** | 시험 코드에는 본 표준 중 FW-CMX, FW-FUN-008, FW-NAM 계열을 완화 적용한다. 단 §9 타입 규칙은 유지한다. |

## 18. 편차(Deviation) 관리 절차

MISRA Compliance:2020 에 따라 다음 3종 문서를 프로젝트마다 유지한다.

### 18.1 Guideline Enforcement Plan (GEP)

각 가이드라인에 대해 **어떤 수단으로 준수를 확인하는가**를 사전에 정의한 표.

| 가이드라인 | 검증 수단 | 비고 |
|---|---|---|
| Rule 17.2 (재귀 금지) | 정적분석 도구 자동 | — |
| Dir 4.1 (런타임 오류 최소화) | 코드 리뷰 + 단위시험 + 동적분석 | 도구만으로 판정 불가 |
| Dir 3.1 (요구사항 추적성) | 추적 매트릭스 검토 | 프로세스 증거 |

### 18.2 Deviation Record

| 항목 | 내용 |
|---|---|
| 편차 ID | `DEV-<프로젝트>-<번호>` |
| 대상 가이드라인 | 예: Rule 11.4 |
| 적용 위치 | 파일 / 함수 / 행 또는 적용 범위 |
| 사유 | 왜 위반이 불가피한가 |
| 대체 검증 수단 | 리뷰, 시험, 분석 등으로 위험을 어떻게 상쇄하는가 |
| 영향 분석 | 안전·보안 영향 평가 |
| 승인자 / 일자 | 소프트웨어 책임자 (안전 관련 시 안전 관리자 공동 승인) |

### 18.3 코드 내 표기

```c
/* DEV-BMS-004: MISRA C:2023 Rule 11.4 deviation.
   메모리 맵드 레지스터 접근을 위해 정수→포인터 변환 필요.
   대체 검증: port 계층 한정, 리뷰 및 HIL 레지스터 접근 시험으로 확인. */
volatile uint32_t * const p_reg = (volatile uint32_t *)CAN0_BASE_ADDR;
```

### 18.4 Guideline Compliance Summary (GCS)

릴리스 시점에 가이드라인별 최종 상태를 요약한다.

| 상태 | 의미 |
|---|---|
| Compliant | 위반 없음 |
| Deviations | 승인된 편차 존재 (편차 ID 목록 첨부) |
| Disapplied | 해당 프로젝트에 적용하지 않음 (사유 필수, Mandatory 는 불가) |
| Violations | 미승인 위반 존재 → **릴리스 불가** |

### 18.5 승인 권한

| 편차 대상 | 승인자 |
|---|---|
| Advisory | 불요 (기록만) |
| Required | 소프트웨어 개발 책임자 |
| Required (안전 관련 기능) | 소프트웨어 개발 책임자 + 기능안전 관리자 |
| Mandatory | **승인 불가** |

## 19. 코드 리뷰 체크리스트

리뷰는 머지 전 필수이며, 결과는 형상관리 시스템에 기록으로 남긴다.

- [ ] 정적분석 신규 위반 0건 / 컴파일 경고 0건
- [ ] 단위시험 통과, 신규·수정 로직에 대한 시험 케이스 추가됨
- [ ] 계층 규칙 위반 없음 (벤더 SDK 격리, 역방향 호출 없음)
- [ ] 모든 공개 함수의 파라미터 검증 존재
- [ ] 반환 오류 코드가 호출부에서 처리됨
- [ ] 고정폭 타입 사용, 암묵적 타입 변환 없음
- [ ] 매직 넘버 없음, 물리량 변수에 단위 표기됨
- [ ] 블로킹 루프에 타임아웃 존재
- [ ] ISR 본문이 최소화되어 있고 공유 변수가 보호됨
- [ ] 동적 할당·재귀·가변 인자 없음
- [ ] 복잡도 한계(§17.1) 이내
- [ ] 편차 발생 시 편차 ID 주석 및 Deviation Record 등록 완료
- [ ] 요구사항 ID와의 추적성 확보 (기능안전 프로젝트)

## 20. 산업별 추가 요구 (델타)

본 표준은 **공통 코어**이며, 아래 항목은 프로젝트 계획서에서 별도로 규정한다.

### 20.1 자동차 (ISO 26262)

- HARA 기반 ASIL 결정 및 안전 요구사항 할당
- ASIL C·D: MC/DC 커버리지, 고장 주입 시험
- Automotive SPICE SWE.1~SWE.6 산출물 및 양방향 추적성
- AUTOSAR Classic 적용 시 BSW 인터페이스 준수
- 도구 자격부여: TCL 결정 및 ISO 26262-8 §11 대응
- 사이버보안: ISO/SAE 21434, UNECE R155/R156

### 20.2 의료기기 (IEC 62304)

- ISO 13485 품질경영시스템 하에서만 본 표준이 유효하다
- ISO 14971 위험관리파일과 소프트웨어 위험통제수단의 추적
- 소프트웨어 안전 등급(A/B/C) 결정 및 등급별 요구 활동 적용
- SOUP 목록, 버전, 알려진 이상, 기능·성능 요구사항 문서화
- IEC 62366-1 사용적합성, 사이버보안(FDA 가이던스, SBOM)
- 시판 후 감시(PMS) 및 문제 해결 프로세스(62304 §9)

### 20.3 산업·기계·농기계

- IEC 61508-3 (SIL) / ISO 13849-1 (PL) / ISO 25119 (AgPL)
- 안전 기능 분리 및 진단 커버리지(DC) 설계
- 정기 자가진단(POST / 주기 시험) 구현 규정

## 21. 도입 및 예외 처리

### 21.1 신규 프로젝트

착수 시점부터 본 표준을 전면 적용한다. `-Werror` 를 처음부터 활성화한다.

### 21.2 기존 프로젝트

다음 단계로 점진 적용하며, 각 단계를 프로젝트 계획서에 일정으로 명시한다.

| 단계 | 내용 |
|---|---|
| 1 | 포맷 통일(`.clang-format`) + 컴파일 경고 정리 |
| 2 | 계층 분리 및 벤더 SDK 격리 (FW-ARC 계열) |
| 3 | 통신 계층 자동생성 전환 (FW-COM 계열) |
| 4 | 정적분석 baseline 설정, 신규 코드 게이트 적용 |
| 5 | `app/` 계층 호스트 단위시험 및 CI 구축 |
| 6 | 편차 문서화 및 GCS 산출, 전면 준수 선언 |

### 21.3 표준의 개정

본 표준의 개정은 소프트웨어 개발 책임자의 승인을 거치며, 개정 시 영향받는 진행 중 프로젝트의 적용 버전을 함께 결정한다. 프로젝트는 착수 시점의 표준 버전을 유지하는 것을 원칙으로 한다.
